## 背景

#84 把 `scriptCapability` 的正例从“文件多”改成“下一步依赖上一步的结果”，并删掉了 “not over one read”。文案变了就必须重测，否则无法区分“措辞变好”与“障碍在别处”。这条规则是 #78/#79/#80 一轮走下来的既定做法。

本任务的对照基线是 #83。

## 目标

用与 #83 完全相同的任务集（任务 1–4）取得 #84 改动后的数字，给出明确“保留 / 收窄 / 回退”判定。

## 实现要点

- 逐字复用 #83 的 cwd、文件布局、provider/model、任务原文、构建方式；只改变构建版本（#84 合入前后）。
- 每个任务每个版本 3 次，报告中位数与跨度。
- 记录：`requests`、`usage.input_tokens`、`script` 调用次数（`NEO_LOG` 里 `"name":"script"`）、大文件内容是否进入上下文。
- **一次只动一个变量**：本任务期间不改 #85 的错误文案、不改 `bash` 的 schema、不给子代理加 `script`。否则数据无法归因。
- 判据事先写死：
  - 任务 2（条件改写）与任务 4（读-判断-改写）的 `script` 调用率上升，且 `requests` 不上升，且 input 增量不超过固定成本（1,455 B ≈ 2,000 tokens）+ #83 记录的噪声底 → **保留**。
  - 调用率上升但 input 明显上升 → **收窄**，回退部分措辞，不收窄工具能力。
  - 调用率不上升 → 障碍不在文案，转 #87（决策点提示）与 #85（失败可教），本任务结论写“文案不是障碍”。
- 数字与预期相反时如实记录，不为特性辩护。

## 验收标准

- 对比表含：任务、`requests` 前/后、input 前/后、相对变化、`script` 调用率（N/3）、结论。
- 结论只包含“保留”“收窄”或“文案不是障碍”三种之一，不含模糊措辞。
- `docs/performance.md` 的“script tool 的实测收益”小节按结果更新，且不与 `docs/design/js-batch-tool.md` §2、§6 的结论矛盾。
- 若判定回退，另开 issue 说明拆除范围，不在本任务里静默删除。

## 判据修正（2026-11-25，依据 #83 的实测与噪声底）

原判据有两处不可执行，先修正再跑，避免事后调整：

1. **“input 增量不超过固定成本（1,455 B ≈ 2,000 tokens）”用了错误的换算。** 1,455 字节按 4 字符/token 约 364 token。这条数字不能作为阈值。
2. **n=3 分辨不出任何有意义的差异。** #83 的实测：`off` 组 input 标准差 2,203、极差 3,871；`on` 组标准差 4,517、极差 13,045。按每臂 n 的粗略估计，要分辨 1,500 token 的差异，`off` 臂需约 35 次、`on` 臂需约 145 次运行；分辨 3,000 token 也需要每臂 9–36 次。以本任务原定的 3 次/臂，requests 与 input 的中位数差异**只能反映模型随机性**。

因此本任务的判定改用**非随机信号**为主，token 数据只作为记录、不作为判据：

- **主判据（布尔）：** 被选中的脚本是否把“读 → 判断 → 写”合并进同一次 `script` 调用。判法：该次运行的日志里存在 `name:"script"` 调用，且该脚本的 `source` 内同时出现至少一个读取类宿主调用（`tools.read_file` / `tools.grep` / `tools.glob`）与一个写入类调用（`tools.write_file` / `tools.edit_file`）。#83 里 2/6 的运行调用过脚本，但合并数为 **0**（其中一次只把 `grep` 换成了脚本，编辑仍在顶层），这是本任务要观察的量。
- **次判据（记录用）：** `script` 调用率、`requests`、`input_tokens` 的中位数与极差，按原样记录并注明不用于判定。
- **运行次数：** 每个版本 3 次（与 #83 同），因为主判据是布尔量而非均值；若三次全为 0 或三次全为 1，结论即可写出，不补跑。
- 判定用语改为三种：**“合并发生”（3/3 或 2/3）**、**“部分发生”（1/3）**、**“未发生”（0/3）**。不再使用“保留/收窄/回退”这类依赖 token 判定的措辞。
- 若“未发生”，结论写“文案改变了判据但没有改变用法”，后续交给 #87（决策点提示）。

**变量控制不变**：本任务期间不改 `bash` 的 schema、不给子代理加 `script`。注意 #85 已合入，其改动只影响失败路径的提示文本，不影响本任务的主判据（合并与否），但需在报告中注明当时包含 #85。

## 实测结果（2026-11-25）

环境与 #83 完全一致：cwd `/tmp/measure/ws4`，同一 fixture、同一任务原文、`commandcode` / `deepseek/deepseek-v4.1-flash`。二进制由本仓库 #84 + #85 合入后构建（`-X main.Version=measure-84`），**同一个二进制**跑本组，只翻转 `features.script`。

按修正后的判据，主指标是布尔量：被选中的脚本是否在同一 `source` 内同时含读取类与写入类宿主调用。

| 运行 | requests | input_tokens | `script` 调用 | 合并读-判-写 |
| --- | ---: | ---: | ---: | --- |
| on r1 | 5 | 14,455 | 0 | — |
| on r2 | 9 | 24,408 | 0 | — |
| on r3 | 5 | 13,792 | 0 | — |

三次运行**一次都没调用 `script`**，三次都走 `bash` +（一次）`edit_file`：

- r1：4 次 `bash`，用 `python3` 就地改行。
- r2：8 次调用，`grep -n` / `sed -n` 定位后顶层 `edit_file`，随后 4 次 `bash` 做校验。
- r3：4 次 `bash`，`sed -i '1501s/…'` 直接改。

## 判定：未发生（0/3），文案改变了判据但没有改变用法

按本 issue 修正后写死的三种用语，结论是 **“未发生”**。

与 #83 的对照值得注意：**同一任务、同一模型，改动后调用率从 2/6 降到 0/3。** 这不能读成“文案改坏了”——#83 已记录该模型上 input 极差达 13,045 token，调用率 2/6 与 0/3 的差异在噪声范围内。能确定的是：**新文案没有把调用率推到可观测的水平**。

结合 #83 记录的行为（`read_file` 全程 0 次，模型自己用 `sed -n` 收窄窗口），结论是文案不是主要障碍：

- 模型并不需要“把文件读回上下文再判断”，它用一条 `sed` 就把窗口收窄到 3 行。
- 因此“下一步依赖上一步结果”这个判据在本任务上**没有需要被脚本替代的往返**——`bash` 已经把它压缩成一次调用。
- 这与 #83 的核心发现一致，并进一步说明：**障碍在于脚本与 `bash` 功能重叠时没有独占优势，而不在于提示词怎么描述。**

## 对下游任务的影响

- **#87（决策点提示）优先级下调。** 它的假设是“模型在选择时刻读不到脚本的判据”。本任务显示模型在决策时刻读到与否并不改变结果，因为它根本不需要脚本。在做 #87 之前，需要先有一个 `bash` 明显不方便的任务（例如按 N 个文件的内容分支后批量改写）。
- **#88（子代理给 `script`）不受影响**，它是能力补齐，不依赖调用率。
- **#89、#90 优先级不变或下调**：两者都建立在“模型本可以脚本化却用了多次调用”的前提上，而本任务里模型用 4 次 `bash` 就完成了任务，没有可观察的浪费。

**需要新开任务的情形**：若要让 `script` 在真实工作中站得住，需要构造一个 `bash` 无法用一行解决、且依赖链真实的场景（多文件、按内容分支、批量改写），并先测 `bash` 在该场景下的基线。这不在本任务范围内，本任务不为特性辩护。
