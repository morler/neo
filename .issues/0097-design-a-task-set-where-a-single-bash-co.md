## 背景

#91 的结论是"补能力"，其中写明再试一次需要换一个**无法用一条 bash 命令完成**的任务。本轮 fixture 是一个断言写错的 Go 模块，而模型用 `sed -i`、`git checkout --` 就能一步到位，这被记为"模型把读、写、验证拆开调用"的重要原因之一。

这不是产品代码缺陷，而是**测量方法的缺口**：在拿到一个真正需要合并的任务之前，无法区分"模型不会合并"和"任务不需要合并"。

## 目标

设计并验证一个任务集，使默认模式**必须**用多条命令或多次往返才能完成，从而让"合并"成为可观测的收益而非可选风格。

## 实现要点

任务必须满足：单条 `bash` 命令无法可靠完成，且正确答案取决于被读取的内容。候选形态：

- **按内容分支的批量改写**：N 个文件各自含不同的标记值，需要按每个文件的内容决定替换成什么，且要求保持其余字节不变。
- **跨文件一致性修复**：改动一个文件里的常量，其他 M 个文件引用了它，需要找出所有引用并同步。
- **诊断后再修**：先跑测试得到失败列表，按失败信息逐个定位并修改，最后复验。

反面例子（本轮已证明无效）：单个断言写错、单个词替换——`sed`/`git checkout` 一步即可。

## 验收标准

- 任务集写入 issue 或 `docs/performance.md`，含逐字任务原文、fixture 布局、验证方式。
- 先用默认模式跑 3 次，确认**没有任何一次**能用单条 bash 命令完成（记录每次的命令序列）。
- 再用 solo 模式跑 5 次，按 #91 预注册的布尔判据记录合并次数。
- 报告中位数与跨度；token 数据只记录不作判据（沿用 #86 的噪声底结论）。
- 不修改产品代码；若结论需要产品改动，另开 issue。


## 结果记录（2026-11-25）

任务集与结果已写入 `docs/performance.md` 的"A task set where one bash command cannot finish"小节（含逐字任务原文、fixture 布局、验证方式）。

fixture：`stats` 模块，`stats.go` 里六个函数各自有文档化行为与一个 bug，`stats_test.go` 每个函数一条测试（修复前 5 条失败）。六个 bug 无共同文本形态（`len(xs)` 代替求和、`xs[0]` 代替最大值、奇偶判断写反、`s[1:2]`、除以 `len(xs)-1`、`>=` 代替严格计数），因此必须先读出函数体才能决定怎么改——这正是"单条 bash 无法完成"的判据来源。

### 本轮最关键的发现

这是所有 fixture 上**首次出现非零合并率**（此前 #83 2/6、#91 1/6、#101 0/3 均为 0）。没有任何一次运行能用单条命令完成：每次都是先读后写，单次调用内 4–10 个子调用。

两种形态区分清晰：
```
合并:   read_file x2 + run + write_file x2       （读、改、验证、再改）
未合并: read_file x4..10 | edit_file x10 | run    （批量读、批量写、验证）
```

合并在本任务上**不比拆分更省**（两者 requests 中位都是 5），区别在形态而非成本。任务集带来的变化是：它让合并**成为可能**——"一次调用写 10 处"是此前 fixture 从未产生的形态，因为它要求先读完 10 个函数体才能写 10 处。

### 结论

不支持再改提示词：任务一旦需要"读的值决定写的内容"，合并在零新增文本下自然出现。任何进一步的提示词改动都只是在测噪声。

未修改产品代码（`go test ./...`、`qlty check` 通过）。

## 更正（2026-11-25 全盘评审）

本 issue 的结果记录有一处错误，已开 #103 跟踪修正：

测量时把 features.codemode 设为 solo，但 solo 在 ad63f36 已被移除，config.Load() 不做校验，于是静默回退成 codemode。因此当时记录的 "codemode (n=3)" 与 "solo (n=5)" 并非两种工具面的对照，而是同一个面的 8 次采样。

原始计数仍然有效（8 次运行、3 次合并），但不能表述为两模式对比。归因错误的根因另见 #104（配置校验缺失）。
