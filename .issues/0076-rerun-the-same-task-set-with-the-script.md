## 背景

原 #62 的第 2 步。基线已在 #75 取得。现在用完全相同的任务集重跑，得出可比较的差异。

结论允许是“保留”或“回退”，两者都是合法结果——`MISSION.md` 明确要求不保留价值未证实的复杂度。

## 目标

产出前后对比表与明确结论。

## 实现要点

- 逐字复用 #75 的命令、模型、cwd、提示；只改变 `script` 是否可用。
- 同样每个任务跑 1 次；结果离群时补跑一次并说明。
- 分别报告：
  - **往返次数**（`requests`）的绝对与相对变化；
  - **input token** 变化，并区分是“少发了几轮”还是“每轮更小”；
  - **大文件内容是否留在上下文**（定性 + 若可测则定量）。
- 判据（在 issue 里预先写死，避免事后调整）：
  - 往返次数未下降，或 token 节省 < 10% → 建议回退或收窄范围。
  - 往返下降且 token 节省 ≥ 10% → 保留。
- 把结论写进 `docs/performance.md` 的 Token Baseline 一节。
- 若判定回退：**另开** issue 说明拆除范围，不在本任务里静默删除。

### 关键观察：模型没有主动使用 script

三次自由运行中，模型全程使用 `bash` 与 `grep`，**从未调用 `script`**。任务 1 的最终回答明确列出了 `find`/`grep -rc` 等命令。

为排除“工具坏了”的可能，我另跑一次显式指令（“You must call script, not bash”）：模型确实调用了它，但产生 **3 次 tool_errors**，过程是：

1. 先假设沙箱提供 `glob` —— 失败。
2. 再尝试裸 `read_file` —— 失败。
3. 再尝试 `await` —— 失败（classic script 无顶层 await）。
4. 最后用 `tools.read_file(...)` 同步写法成功。

即：工具可用，但**发现成本高**，且在自然语言任务中模型不会主动选择它。

## 结论：收窄（不保留当前形态，也不整体回退）

按本办法预先写死的判据——往返次数未下降，或 token 节省 < 10% → 建议回退或收窄：本轮 **requests 变化为 0%，input 反而上升 6.7%–10.6%**，判定为 **收益未证实**。

选择“收窄”而非“回退”的理由：

- 机制本身是完整且经过验证的（白名单、审批、资源限制、可观测性都有测试），拆除会浪费这部分工作。
- 实测暴露的是**两个具体可修问题**，不是设计失败：
  1. 提示词没有说清 API 形态（`tools.` 命名空间、必须同步、无 `glob`/`await` 的写法），导致模型试错 3 次。
  2. 固定成本（schema 704 B + 提示 439 B）在每个任务上都摊到了 input 里，而收益只在模型主动写脚本时出现。

因此建议：

- **不默认注册**：把 `script` 从 `chatRegistry`/`newRegistry` 的默认集合移出，改为显式开启（例如 `--script` 或配置项），使不使用它的会话不付固定成本。这一步直接把上面 +6.7%–10.6% 的 input 增量归零。
- **保留代码与测试**：白名单、审批、限制、事件、TUI 全部保留，开启后即可用。
- **改进提示词后再测一次**：提示词需写清 `tools.` 前缀与同步约束；这是本次实测中最直接的失败原因。

由于判定为“收窄”而非“回退”，不需要另开拆除 issue；但“是否默认注册”属于产品决策，应在新 issue 中单独跟踪。
