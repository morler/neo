## 背景

Maki 的 `code_execution` 将中间结果留在解释器中，只把脚本明确返回或打印的内容送入模型上下文。Neo 默认 codemode 已支持这条路径，但仍可能把多个文件窗口或整段日志拼进最终结果。旧实验（#76、#97、#103）主要比较工具面或合并调用，没有隔离最终回传体积。

## 实验与预期收益

使用现有 `script`，比较直接回传输出与在脚本内筛选后仅回传结论和必要证据（计数、文件位置、少量命中或错误片段）。目标是减少后续请求重带的历史，不把工具结果占比当作可节省比例。先不改常驻 prompt、工具 schema、全局输出上限或执行器。

## 验收标准

- 固定可重复的跨文件查找和长日志定位 fixture，另设已知行号窄读负对照；写明提示、判分证据和两组唯一变更，不拿全文件读取当唯一基线。
- 固定 provider、model、effort 和运行条件，多次运行，报告成功率、请求数、最终工具结果字节及 provider 的 input/cache creation/cache read/output；后端未提供缓存分项则标明。非模型测试使用 stub，不依赖网络。
- 对结果字节变少但补读或失败变多的情况单独报告；只有在任务成功率不降且端到端用量下降时才建议后续产品改动。允许结论为不引入。


## 结果记录（2026-11-28）

完整记录、fixture、harness 与逐次原始结果：`docs/measurements/132-evidence-only-script-results/`，摘要已并入 `docs/performance.md` 的 Token Baseline 一节。

**环境**：`provider: commandcode` / `deepseek/deepseek-v4.1-flash` / `reasoning_effort: low`，code mode + `features.script: true`，二进制 `nightly-20261127-da511a0-2-gcd84837`。3 个 fixture × 2 臂 × 5 次 = 30 次运行。**该后端不报告缓存分项**：所有运行 `cache_creation_tokens = 0`、`cache_read_tokens = 0`，所以报告里没有缓存比例，也没有估算。

**两组唯一变更**：只有提示最后一句不同。full 臂要求"引用失败行及足够的上下文，逐字照抄"；evidence 臂要求"只给行号、错误文本、拒绝连接的 host 和 port，不要粘贴日志内容"。fixture 字节、provider、model、effort、工具面、二进制全部相同。

**非模型校验**：`check.sh` 用合成请求/结果日志校验归约器，`grade_check.sh` 用 6 个合成答案校验判分器（正确答案过、缺证据的不过）。两者都不联网、不调模型。日志 fixture 由 `make-log.sh` 确定性生成，仓库里存 20 行生成脚本而不是 259 KB 文件。

### 三个 fixture 的结论分开写

- **长日志定位**：方向一致且幅度最大（工具结果字节 −86%，prompt −67%，requests 7→4），但范围边缘仍有重叠（full 最小 3,125，evidence 最大 1,114），所以只能说"一致的显著差异"，不能说"阶梯式变化"。
- **跨文件查找**：中位数下降，但 5 次里有 2 次仍然读了整个 fixture（66,372 / 68,366 字节），虽然提示明确要求不要粘贴文件内容。中位数由 3 次窄查找撑起来，不能当作稳定效应。
- **已知行号窄读（负对照）**：**反向**。evidence 臂反而用了更多工具结果字节（中位 5,073 vs 902）和更多 requests（中位 3 vs 2），而最终回答更短。模型为了回答"第几行、值是多少"把 120 行文件整个读了，因为那句话只约束怎么写、不约束怎么读。

### 观察到的机制

1. **raw 读不可分页**：`read_file({raw: true})` 撞上 `selection exceeds the byte cap; retry with offset=1013, limit=506`。这是设计使然（259 KB > `MaxReadBytes`），但 full 臂多次在这里多花一跳；evidence 臂改用 grep 避开了它。这是"每次尝试的发现成本"，不是两臂的设计差异。
2. **提示只影响写多少，不稳定地影响读多少**：跨文件两个臂都收敛到 glob + 全量 read_file；窄读里 full 臂因为"引用十行"而窄读，evidence 臂因为"只要值"而整读。

### 结论：不引入产品改动

issue 预先写死的判据是"任务成功率不降 **且** 端到端用量下降"才建议产品改动。成功率保持，但端到端用量没有一致下降：一个 fixture 明显下降、一个仅中位数下降且极值重叠、一个反向。能买到长日志形态的提示规则，同时会把负对照翻过来，本样本无法证明可以只买前者。因此**不引入**，未改动 prompt、工具 schema、输出上限或执行器。

测量支持的更窄结论是：Neo 的 script 工具**能够**只回传证据，且在大型日志任务上节省很大；缺的是选择，不是能力——这与 #83/#86/#91 记录的"提示词改动不能可靠移动选择"一致。

### 其他

- 归档时 Go fixture 以 `.go.txt` 存放，`run.sh` 在 staging 时改回 `.go`；否则仓库根的 `go test ./...` 会把测量 fixture 当成真实包编译而失败。
- 报告写完后另跑 2 次 `verify` 复跑（已在 `results/`，不计入 5 次样本），确认提交后的 harness 从干净检出仍可运行；负对照方向复现，绝对值不复现，与报告声明的噪声底一致。
