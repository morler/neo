## 背景

`internal/agent/agent.go` 目前没有重复调用检测。`DefaultMaxTurns` 的注释（`agent.go:117`）明确说它只是 runaway loop 的安全熔断，不是正常运行路径。模型若陷入重复调用，现在唯一结果是把轮次烧到上限，每轮都是一次完整请求加一次完整执行。

killi 用日志证据支撑了分级策略（decisions 26、31）：3/5/7 的提醒会被部分模型忽略，所以提醒阈值要更晚、停止阈值要更靠后。

## 范围（合并自原 #43 + #51）

计数键、提醒注入、阈值判断三者是同一套代码，拆成两条只增加协调成本。本任务用一个阈值表完成从提醒到终止的完整梯度：

| 第 N 次相同调用 | 行为 |
| --- | --- |
| 3、5、8 | 追加一条 `<system-reminder>`，工具照常执行 |
| 12 | 不执行该工具，结束本轮并给出可读原因 |

## 实现要点

1. 计数键：工具名 + 参数 canonical JSON 的哈希。**不要**保存完整参数（killi decision 35 记录了这笔内存开销）。
2. 每个用户轮次开始时重置，跨轮不累计：同一句 `go test` 十分钟后再问不算重复。
3. 第 3、5、8 次注入 `<system-reminder>`，**追加在会话末尾**，绝不改系统提示词、工具列表或历史——这是 `docs/design/token-budget.md` 原则 1，也是缓存前缀不失效的前提。
4. `workflow`、`goal` 这类状态类工具是否计入，要在代码注释里明确写出决定与理由（建议计入：它们同样消耗轮次）。
5. 只在 `Messages` 末尾追加，不动已有消息的字节；注入内容要短（一到两行），说明「这是第 N 次相同调用」并建议换一种做法。
6. 第 12 次在第 **执行前**判定，避免浪费一次工具执行。终止必须产生 TUI 可见的事件（复用 `EventError` 或语义明确的新事件），错误信息包含工具名与次数，不要静默返回空字符串——用户要能区分「这轮被熔断」和「我按了 esc」。
7. 与 `MaxTurns = 500`（`agent.go:120`）的关系写进注释：`MaxTurns` 是外层安全阀，本熔断是内层针对性保护，互不替代。

## 验收标准

- 单测覆盖第 3、5、8 次：各注入恰好一次提醒，且工具仍被执行。
- 单测覆盖第 12 次：不执行工具（用计数桩验证实际调用 11 次），本轮以可读错误结束，事件到达处理器。
- 单测覆盖第 11 次：仍正常执行并注入提醒。
- 断言每次注入后，系统提示词与工具定义的 JSON 逐字节不变。
- 一个用户轮次结束后计数归零：两轮之间各调用两次相同工具不触发。
- 不同参数的同名工具交替调用不触发（键不同）。
- `go test ./internal/agent/ -race`、`go vet ./...`、`qlty check --all` 通过。
- 在 `docs/developer/tools.md` 说明这条保护与阈值。
